# VOLTORA legacy backend – source-evidenced findings

Scope: `/tmp/handoff/src/backend` (read-only; FastAPI + Motor/MongoDB; ~18.7k LOC non-test Python, 70 modules). All paths below are relative to `/tmp/handoff/src/backend` unless prefixed. Evidence is by reading source; **nothing was executed** (no tests run, no DB). Items I could not confirm are marked **UNCONFIRMED**. Route counts come from `/tmp/handoff/VOLTORA_endpoint_inventory.json` (346 routes; I re-derived per-file counts and they match).

Conventions that matter for every port:
- **Money = integer minor units (poisha, 1 BDT = 100)** everywhere (`schemas.py:18,57-59` `price:int`; `commerce.py:57` `rounded()` = `Decimal.quantize(1, ROUND_HALF_UP)`; gateways divide by 100: `bkash.py` `f"{order['total']/100:.2f}"`, `sslcommerz.py` same). Seed currencies: BDT decimals 0, USD/EUR display-only rates (`seed.py:154`). Tax rates and loyalty rates are floats.
- **IDs**: `core.uid()` = `secrets.token_hex(12)` (24 hex chars) (`core.py` `uid`). Exceptions: first owner `id='initial-owner'` (`auth.py:~133`); installer owner `uuid4().hex` (`installer.py:125`); location ids are prefixed strings `div:`/`dis:`/`upa:`/`uni:`/`area:` + slug; theme/role/provider rows use slugs.
- **Timestamps** are ISO-8601 *strings* (`core.stamp()`), compared lexicographically in queries (e.g. `commerce.py:243` `coupon['ends_at']<stamp()`); TTL-indexed `expires_at` fields are real `datetime`s. Mixed types are a migration trap.
- **Collection naming**: every access goes through `ScopedDatabase` → `PREFIX + (workspace_ns + '_') + name` (`core.py` `ScopedDatabase`); production prefix is `REBUILD_COLLECTION_PREFIX` (installer writes `v1_`, `installer.py:214`). Demo "workspaces" (`isolation.py`) are legacy and disabled for new sessions (`isolation.py:~13` returns 401 for `voltora_workspace` cookie) – **do not port**.

## 2. Auth & RBAC

**Accounts.** Customers and staff share ONE `users` collection, distinguished by `role` (`'customer'` vs any other; `auth.py:64,66`). Owner id `initial-owner` created via `/api/auth/setup` (`auth.py:128-143`, requires env `OWNER_SETUP_KEY`, `compare_digest`, password ≥12, one owner enforced by `find_one({'role':'owner'})` + unique indexes). Customer registration needs feature flag `registration` and password ≥10 (`auth.py:150-156`). Staff are created by password in `POST /api/admin/team` (`admin.py:749`, password min 12, `mfa_enabled:False`).

**Password hashing**: `argon2.PasswordHasher()` library defaults (`auth.py:16`; `hasher.hash` `auth.py:138,152`). `VerifyMismatchError|InvalidHashError` → invalid (`auth.py:179-181`). No rehash-on-login. Login timing: user-not-found skips hash verify (user enumeration by timing – minor, **UNCONFIRMED** measure).

**Sessions/cookies**: opaque token `secrets.token_urlsafe(40)`; only `sha256(token)` stored in `sessions.token_hash` (`auth.py:101-104`). Cookie `voltora_session`, HttpOnly, SameSite=Lax, path `/`, `Secure` unless `APP_ORIGIN` scheme is `http` (`auth.py:106-112`). TTL: **1 h for staff, 24 h for customers** (`auth.py:103`), absolute (no sliding refresh found). Session doc embeds the role's permission list (`auth.py:104-105`), but `optional_user` recomputes permissions on every request from role+grants (`auth.py:87`), so the "revoke sessions on role edit" in `roles.py` is belt-and-braces. Banned/disabled users are rejected at session resolution (`auth.py:78-83`).

**CSRF**: double-submit-ish: per-session random `csrf` stored on the session, returned in JSON (`auth.py:113,121`), required in header `X-CSRF-Token` on every non-GET/HEAD/OPTIONS request that uses `current_user` (`auth.py:94-95`, `compare_digest`). Plus Origin allowlist middleware on unsafe methods **only when an Origin header is present** (`server.py:128-132`) and body cap 11 MB by Content-Length only (`server.py:133-135`). Guest endpoints (checkout, payment verify, order lookup) use `optional_user` and are CSRF-exempt by design (bearer = signed order link).

**MFA**: TOTP via `pyotp`, secret Fernet-sealed with `APP_SECRET`-derived key (`vault.py`: `Fernet(urlsafe_b64(sha256(APP_SECRET)))`) – a single static key, no rotation, no KDF salt. Enrolment `/mfa/enroll` → `mfa_pending`; `/mfa/verify` accepts TOTP (`valid_window=1`) with replay protection via `mfa_last_step` conditional update (`auth.py:~268-276`) or recovery code (10 codes, `xxxx-xxxx`, stored as `sha256('mfa-recovery:'+code)`, spent with one conditional `$pull`, `auth.py:42-60`). **Staff cannot do anything until a MFA-verified session exists**: `authorize()` requires `session_mfa` for every non-customer (`permissions.py:68-73`); `current_user` blocks all routes except `/mfa/verify` and `/logout` for any user who has MFA enabled but not yet verified (`auth.py:97-98`). A staff user without MFA enrolled can still reach `/mfa/enroll` (via `current_user`, no `require`). Installer-created owner has `mfa_enabled:True` with secret pre-set (`installer.py:130-131`).

**Rate limits / lockouts**
- Login lockout: ≥8 failed attempts per `sha256(email)` within 15 min → 429 (`auth.py:throttle`, ~L118-123); same throttle reused for MFA keyed `mfa:<user_id>`; attempts logged to `login_attempts` (TTL 90 d). Keyed by email only, not IP.
- Edge limiter (non-GET only, per client IP per minute, Mongo `find_one_and_update` counter, `server.py:136-147`): `RATE_LIMITS` (`server.py:89-109`): demo/start 10, auth/login 20, auth/register 10, auth/setup 10, auth/otp 30, auth/password 10, orders/lookup 10, gift-cards/lookup 10, cart 60, checkout 20, products 20, auth/oauth 60, support/conversations 60, newsletter 20, affiliate/apply 5, affiliate/status 10, events 120, locations/resolve 120, customer/privacy 10. **No limit on `/api/orders/{id}/payment/verify`, `/admin/*`, GET endpoints.** Client IP = `request.client.host`; Dockerfile runs uvicorn with `--proxy-headers --forwarded-allow-ips='*'` (`deploy/Dockerfile.api` CMD) so the app trusts X-Forwarded-For from any peer; `deploy/docker-compose.yml:75-80` publishes only Caddy (80/443/udp443), so exposure depends on Caddy overwriting the header (**UNCONFIRMED** in Caddyfile) — rate limits are only as good as that.
- OTP: 6-digit, `issue_code` stores sha256(code), 5 min TTL, max 5 attempts, single use (`auth_ext.py:35-49`); `otp/send` returns `{ok:True,sent:False}` for unknown users (no enumeration) but has no per-target send throttle other than the 30/min IP bucket.
- CAPTCHA enforced on login/register (`auth.py:162-164`) via pluggable provider (`captcha.py`).
- Other: Security headers + CSP in `server.py:119-157`; `Cache-Control: no-store` for `/api/auth|admin|orders|customer|support`.

**Staff vs customer extras**: OAuth (google/facebook/apple) creates **customer** accounts only, auto-link disabled (`auth_ext.py:401`). Staff session sees `workspace_path` (an "unlisted entrance", default `/w-k4q9v2mx`, `auth.py:68`) – security-by-obscurity, do not port. Email verification flag `email_verified`; phone unique sparse index (`seed.py:108`).

## 3. Commerce rules (to port)

Everything below is in `commerce.py` unless stated. `calculate()` (L199-303) is the single pricing function used by `/cart/quote` (L352) and `/checkout` (L829); the server never trusts client prices (client sends `expected_price`, mismatch → 409, L215). A leading `~` on a line number means "approximately, within a few lines".

### 3.1 Cart / quote pricing (`calculate`, L199-303; request model L24-55)
Input `Quote`: `items[1..50]{product_id, variant_id, quantity 1..50, expected_price}`, `shipping_id` (default `'dhaka'`), `coupon`, `email`, `location: Address|None`, `redeem_points`, `use_credit`, `gift_code`, `gift_message`, `gift_wrap`. A signed-in user's saved bag lives on `users.bag[]` (`commerce.py:331-350`, `PUT /api/cart`).
Order of operations:
1. Store must be `settings.mode=='live'` else 503 (L201). Duplicate variants rejected (L202).
2. Per line: product must be `published`; `core.sale_price()` first (a lapsed flash sale reverts price to `compare_price`); variant price must equal `expected_price`. Stock = `inventory{id:'main'}.quantities[variant_id]` (one document).
3. Bundles (`product.bundle.items`): sold at the bundle variant's own price; pieces expanded into extra rows (`expand_bundle` L151-167), each stock-checked; `bundle_discount = Σpiece totals − bundle price×qty`, clamped `max(0,…)`. A set and one of its pieces cannot share a bag (L224).
4. Tier ("buy more") discount per line: `tier_percent(product.tiers, qty)` (`catalog.py:43`) → `saving = rounded(gross*percent/100)`. Tiers: `{min_qty 2..50, percent (0,90]}`, ≤5 per product, unique `min_qty` (`schemas.py:32-36,102-107`).
5. Pre-order: if stock < qty and stock<=0 and `product.preorder.enabled` with real `ships_at` (YYYY-MM-DD) and qty ≤ `limit` (0 = unlimited) → line flagged `preorder:True, ships_at`; pre-order lines never touch inventory (L169-197, ~886-892).
6. `subtotal = Σ line.total` (pre-discount).
7. Coupon (3.2). 8. Points & credit (3.6, signed-in only). 9. Gift card (3.5). 10. Shipping (3.3). 11. Gift wrap fee = `settings.gift_wrap_fee` if requested (L296). 12. Tax (3.4).
13. `total = net + shipping + wrap_fee + (0 if tax_inclusive else tax)` where `net = subtotal − bundle_discount − tier_discount − coupon − points − credit − gift_card` (L291-299).

Contradiction (defect): the gift card is documented as "money, not a discount" (`giftcards.py:2-4`, `commerce.py:276-277`) yet it is subtracted **before** tax, so the tax base shrinks by the gift-card value. Shipping and gift-wrap fee are never taxed (also assumed by `tax_fraction` L1450-1456 and `invoice_tax` L1463).

### 3.2 Coupons (L233-255; model `admin.py:524-535`; admin CRUD `admin.py:582-630`)
Doc: `{id, code (^[A-Z0-9-]{2,30}$), type:'percentage'|'fixed', value:int(>0; no upper bound for percentage), min_spend(minor), max_uses(default 100), used:int, max_per_customer(0=unlimited), enabled, starts_at, ends_at (ISO strings), product_ids[], category_ids[]}`.
Validation order/messages: feature `coupons` on; code exists (`strip().upper()`); `enabled`; `starts_at>now` / `ends_at<now` (string compare); `used >= max_uses` → fully redeemed; per-customer cap counts the buyer's orders with that `coupon` whose status is not `cancelled|failed`, keyed on `user_id` or case-insensitive `customer.email` (L238-246; indexes `seed.py:84-85`); `subtotal < min_spend` → "Add X BDT more" (**compares the pre-tier subtotal**, L248); eligible base = Σ(line.total − tier_saving) over lines matching `product_ids` AND `category_ids` (both must match when both are set, L251; `category` on a line is the product's category string); none eligible → reject. `discount = min(eligible, percentage ? rounded(eligible*value/100) : value)` then capped at `subtotal − bundle − tier` (L253-255). One coupon per order. Redemption is atomic at checkout: `find_one_and_update({code, enabled:True, $expr:{$lt:['$used','$max_uses']}}, {$inc:{used:1}})` (L903-908); only a **checkout-time failure** decrements (L919). **Cancellation / expiry / refund never decrement `used`** (grep `'used':-1` finds only `commerce.py:919`) → defect (§11).

### 3.3 Shipping fee & delivery zones, Bangladesh (L257-290; `schemas.py:274-284`; seed `seed.py:157`)
`settings.shipping[]` (max 20): `{id ^[a-z0-9-]+$, name, fee(minor, ≤1,000,000), free_above(minor, 0=never), estimate, enabled, divisions[], districts[] (≤200), courier(provider id or '')}`.
Seed defaults: `dhaka` "Inside Dhaka" fee **8000 (৳80)**, free_above **500000 (৳5,000)**, `districts=['dis:dhaka']`; `outside` "Outside Dhaka" fee **15000 (৳150)**, free_above 500000, districts = the other 63 districts of `bd_locations.json` (`seed.py:9-18`); `pickup` fee 0, no zone.
Rules: zone must be `enabled`; `pickup` needs `features.pickup`, others `features.shipping` (L283). `zone_matches` (L66-74): empty `districts` and `divisions` = covers everywhere; otherwise a **structured location is required** and its `district_id` must be in `districts` (districts take precedence over divisions). So with no structured address, `dhaka` and `outside` both fail with "does not cover the selected address" and only pickup works. `validated_location` (L101-130) rejects inactive locations and child/parent mismatches for division→district→upazila→union→area (anti zone-spoofing). Fee = `0 if free_above and paid_so_far >= free_above else fee`, `paid_so_far = subtotal − all discounts − gift card` (L287-288). Courier-backed zones: fee overridden by `provider_configs.config.charge` (string→int) unless free-shipping applies (L289-294); quote fails if the courier isn't connected. No weight/volume, COD fee or surcharge rules exist. Charging currency is BDT only; `currencies[].rate` is display-only (USD 0.0082, EUR 0.0076 in seed).

### 3.4 Tax / VAT (L76-97, L295-299, L1445-1535; `schemas.py:466-472`, `497-500`)
`settings.tax_rate` (default **0**, float %), `tax_inclusive` (default True), `tax_zones[] {label, areas[] (location ids of any level), rate, inclusive}` (≤40). `tax_zone()` checks `area_id → upazila_id → district_id → division_id` in that order and returns the first zone whose `areas` contains it (zone list order breaks ties). Inclusive: `tax = rounded(net*rate/(100+rate))`, not added; exclusive: `tax = rounded(net*rate/100)`, added. The order stores `tax, tax_inclusive, tax_label, tax_rule` (position key `v1:<index>`; comment at L88-97 admits deleting a rule shifts keys). **No Bangladesh 15% VAT preset, no per-product tax class, no BIN/Mushak invoice numbering.** Tax summary/CSV: L1170-1200, 1491-1560.

### 3.5 Gift cards (`giftcards.py`)
Code `VOLT-XXXX-XXXX` (alphabet without 0/O/1/I, `secrets.choice`, 40 bits); doc `{id, code, initial, balance, status:'active'|'spent', note, created_at, created_by, order_id, uses:[{order_id, number, amount(±), at, action:'redeemed'|'restored'}]}`; unique index on `code` (`seed.py:110`). Redeem = conditional `update_one({code, status:'active', balance:{$gte:amount}}, {$inc balance −amount, $push uses})`, then status→`spent` at 0 (`redeem_card`). Restore on cancel/failed checkout is idempotent through the order flag `gift_restored` (`restore_gift`) and re-activates the card. Gift-card products (`product.gift_card`) mint one card per unit when the order is paid, once per order (`mint_for_order`, called from `payments.mark_paid` L57 and COD/bank confirm ~L1789). No expiry, no currency field. Defect: checkout stores `gift_discount` from the quote while `redeem_card` re-clamps to the live balance and the order isn't corrected (`commerce.py:~893-897`).

### 3.6 Loyalty points & store credit (`accounts.py:1-66`; checkout `commerce.py:262-274, 909-930`)
- **Accrual**: only when `features.loyalty` and the order has `user_id`, at the moment payment becomes `paid` (online `mark_paid` or staff confirm of COD/bank): `points = int(total/100/100 * loyalty_earn_rate)`, i.e. `loyalty_earn_rate` points per ৳100 of order **total (incl. shipping/tax)**, truncated (`accounts.py:35-50`; default 1, range 0..100). Idempotency is find-then-insert on `loyalty_ledger.event_id='earn:<order_id>'` (**no unique index → race**; `seed.py:145` indexes only `user_id`).
- **Redemption**: `features.loyalty`; point value `loyalty_point_poisha` (default **50 poisha = ৳0.50**, range 1..1000); `points=min(requested, wallet.points)`; `capped=min(points*poisha, round(0.5*(subtotal−bundle−tier−coupon)))`; `points_redeemed = capped//poisha` (L262-270). Debit is a conditional `$inc` (`points>=n`) in checkout (L909-917); ledger row `{id,user_id,delta,reason,order_id,created_at}` (L919-923).
- **Store credit**: `users.credit_balance` (minor units) + `credit_ledger`; usable up to the remaining payable (L271-273); credited by return resolution `credited` (`accounts.py:~415-420`) and staff adjust (`accounts.py:165-186`, rejects negative balances).
- **Revocation**: `loyalty_revoke` reverses the earn entry once (`event_id='revoke:<id>'`) on cancel, full refund and credit-return (`accounts.py:53-65`; `commerce.py:644`). Partial refunds do not revoke. Points/credit **spent at checkout are never returned when the order is cancelled or expires** (`cancel_order` L636-651 releases stock, gift card, affiliate and loyalty-earn only) → defect.

### 3.7 COD & payment-method rules
Method enum (`schemas.py:285`, `commerce.py:49`): `cod, bank_transfer, stripe, sslcommerz, bkash, nagad, rocket, upay, paypal`; each has `min_amount`/`max_amount` (defaults 0 / 100,000,000) checked against the total (L869). `cod` and `bank_transfer` have no provider; `bank_transfer` needs non-empty `instructions` (L868) and customers can submit a reference (`/orders/{id}/bank-reference`, L1066). Online methods need a *connected, environment-matching, (schema v2) workflow-verified* provider row (`providers.payment_config` `providers/__init__.py:139`, `operational_row` L68-85); the feature switch is `features.get(method_id, features.online_payments)` (L866) — `Features` has no per-gateway keys, so it falls back to `online_payments` (default False). In non-production `RUNTIME_MODE` only COD is accepted (L833-835). COD: no fee, no deposit; order starts `pending` (online/bank: `awaiting_payment`, L923); staff "confirm" marks it `paid`; COD orders may ship/deliver while `unpaid` (L1727). Courier COD amount is typed by staff per shipment (`couriers.py:54 cod_amount`, default 0), never derived from the order total.

### 3.8 Order number & lifecycle
- **Number**: `'VT-' + id[:8].upper()` with `id=uid()` random hex (L880) → 32-bit random suffix, not sequential, **no unique index on `number`** (orders are unique-indexed on `id` and `idempotency_key` only, `seed.py:~90-93`). PO numbers `'PO-'+uid()[:6].upper()` (`purchasing.py:175`). Transaction id `'tx'+uid()[:16]` (L876).
- **Idempotency**: header `Idempotency-Key` (16..100 chars) + sha256 of the request body stored as `request_hash`; replay returns the same confirmation, different body → 409 (L835-846); unique index on `idempotency_key` guards races (L886-888).
- **Statuses**: `initiating` (hidden from admin lists, `ADMIN_ORDER_EXCLUDE` L1121), `failed`, `pending` (COD), `awaiting_payment`, `processing`, `packed`, `partially_shipped`, `shipped`, `out_for_delivery`, `delivered`, `on_hold`, `cancelled`. `payment_status`: `unpaid, awaiting_review, paid, rejected, partially_refunded, refunded`.
- **Allowed transitions** (`commerce.py:1710`; **duplicated verbatim** as `ORDER_TRANSITIONS` at `couriers.py:42`):
```python
TRANSITIONS={'pending':['processing','cancelled','on_hold'],'awaiting_payment':['cancelled','on_hold'],'processing':['packed','cancelled','on_hold'],'packed':['shipped','partially_shipped','cancelled','on_hold'],'partially_shipped':['shipped','out_for_delivery','delivered','cancelled','on_hold'],'shipped':['out_for_delivery','delivered','on_hold'],'out_for_delivery':['delivered','on_hold'],'on_hold':['processing','cancelled'],'delivered':[],'cancelled':[]}
```
  Side rules: moving to `processing|packed|partially_shipped|shipped|delivered` on a non-COD order requires `payment_status=='paid'` (L1727; also `couriers.advance_order_status`); `awaiting_payment→processing` only through payment confirmation (`payments.mark_paid` L36-37, COD/bank confirm ~L1778), not via TRANSITIONS; `shipped/out_for_delivery` cannot be cancelled. Writes use compare-and-set `update_one({'id', 'status': old})` (L1737). `history[]` entries `{status, at, note, actor}` and `internal_notes[]` are embedded arrays.
- **Customer cancel**: allowed in `pending, awaiting_payment, processing` and not when `payment_status in (paid, partially_refunded)` (`CUSTOMER_CANCELLABLE`, `customer_cancel_block` L620-634). Staff cancel of a **paid** order does not require or trigger a refund (L1717-1735).
- **Unpaid expiry**: `UNPAID_ORDER_HOURS` (env, default 48) and `PAYMENT_REMINDER_HOURS` (env, default 6) (L654,657); `start_expiry_worker` (L789) cancels `awaiting_payment`+`unpaid` orders past the window and sends one reminder (`reminder_at`). **`initiating` orders (crash between insert and reservation) are never swept**, and their reservation (if any) is never released: the sweep filter is only `awaiting_payment` (~L773).
- **Guest access**: link token `[ns.]hmac_sha256(APP_SECRET, ns+order_id+idempotency_key+exp).<exp>`, 30-day expiry (L357-378), required for guest order view, cancel, return, payment verify/retry, support attach. `/orders/lookup` by number+email (10/min/IP).

### 3.9 Stock reservation / release / decrement
Inventory is **one Mongo document** `inventory{id:'main', quantities:{variant_id:int}, reservations:{order_id: iso_ts}}`. Stock is **decremented at checkout (reservation = decrement)**, not at shipment. Atomic reservation (`commerce.py:895-904`):
```python
query={'id':'main',f'reservations.{id}':{'$exists':False}}
inc={}
for item in stocked:
    query[f"quantities.{item['variant_id']}"]={'$gte':item['quantity']}
    inc[f"quantities.{item['variant_id']}"]=-item['quantity']
reserved=await db.inventory.update_one(query,{'$inc':inc,'$set':{f'reservations.{id}':stamp()}}) if stocked else None
if stocked and not reserved.modified_count:  # -> restore gift card, order.status='failed', 409
```
Release (cancel / failed / expiry) `release_inventory` L600-617, idempotent because conditional on the reservation key still existing:
```python
released=await db.inventory.update_one({'id':'main',f"reservations.{order['id']}":{'$exists':True}},{'$inc':increments,'$unset':{f"reservations.{order['id']}":''}})
```
(`restore_gift` runs before that guard but has its own flag.) On `delivered` the reservation key is merely `$unset` (no stock change; `commerce.py:~1740`, `couriers.py:~203`), so a later cancel cannot re-release. Ledger `stock_movements{id, type:'reservation'|'cancel'|'return'|'adjustment'|'purchase', created_at, actor, reason, + (order_id, items[]) OR (variant_id, adjustment)}` — two shapes. Manual adjust `admin.py:343-370 stock_delta` refuses results <0 via a `$gte` guard and notifies waiting buyers on 0→positive (`stock_alerts`). Return restock is claimed once via `return_requests.restocked_at` (`accounts.py:~432-441`, `restock()` `commerce.py:819`). PO receive uses `stock_delta(kind='purchase')`. `orders.stock_released:False` is written but never read (dead field, `commerce.py:880`, `offers.py:305`). Hotspot: all variants contend on one document (16 MB BSON cap) → in Postgres use `inventory_levels(variant_id, on_hand, reserved)` with `CHECK (on_hand >= 0)` and per-order reservation rows.

### 3.10 Returns / refunds
- **Return request** (`accounts.py:189-262`): feature `returns`; order status in `delivered|shipped|out_for_delivery`; one open request per order (`requested|approved|received`); **window `settings.return_window_days`, default 14 (0 = none, ≤365)** measured from the latest `history` entry with `status=='delivered'` (fallback `updated_at`), else 409 (L233-240; no deadline is enforced if there is no delivery stamp, which is the case for `shipped`/`out_for_delivery` orders); items must belong to the order, be unique, with optional `quantities{variant_id:n}` ≤ ordered. Row: `{id, order_id, order_number, user_id, email, items[variant_id], quantities{}, reason, status, resolution, note, created_at, updated_at, settled_amount?, restocked_at?}`. States `requested, approved, rejected, received, refunded, credited` (`RETURN_STATES` L265); **no transition validation** — staff may set any status except changing an already-settled one (`accounts.py:384-385`). Settling (L386-452): units/money cannot be claimed twice across the order panel and the returns queue (`claimed_units`, `refund_balance` `commerce.py:1294-1307`); amount = Σ requested units × stored price + tax share (`return_amount` → `refund_gross`); online refunds need `payments.refund` and call `payments.issue_refund`; COD/bank refunds are booked manually; `credited` adds store credit and revokes loyalty; restock happens on the first of `received/refunded/credited`.
- **Refund paths**: (a) `POST /api/admin/orders/{id}/refund` online (`payments.py:222`), (b) `POST /api/admin/orders/{id}/items/refund` line refund (`commerce.py:1638`), (c) `POST /api/admin/orders/{id}/payment {action:'refund'}` for COD/bank (`commerce.py:1762`), (d) return resolution (`accounts.py:381`). Order-side ledger: `orders.refunds[{id, at, amount, tax, lines[], note, actor, method, return_id?}]`, `orders.refunded_amount` (running total), `payment_status` `partially_refunded|refunded` (`refund_rollup` L1445; `refund_status` L1318 — also `refunded` when no refundable unit remains even if the shipping fee was never refunded). Line refunds never refund shipping/gift-wrap. Revenue states `REVENUE_STATES=('paid','partially_refunded','refunded')` (L1325), `net_revenue` L1327-1340. Affiliate conversion is voided and loyalty revoked on full refund.

### 4.3 Audit findings re-checked
- **P-01 (Stripe `parse_webhook` signature mismatch) — CONFIRMED, and wider than stated.** `payments.py:174` calls `adapter.parse_webhook(payload, dict(request.headers), creds, sandbox=config.get('sandbox', True))`. `stripe.py:137` is `parse_webhook(self, payload, headers, credentials)` (no `sandbox`) → `TypeError` → 500 for every Stripe webhook. **bKash has the same defect** (`bkash.py:137` no `sandbox`), but bKash returns None anyway and `supports_webhook=False`, so only Stripe is impacted. `base.py:107`, `sslcommerz.py:132`, `paypal.py:155` have the kwarg. Courier base `parse_webhook` (`base.py:131`) has no kwarg and `couriers.py:229` doesn't pass one (consistent).
- **P-02 (bKash `trxID` never persisted) — CONFIRMED.** `bkash.verify` returns only the string `'paid'` (L100-118); the execute body (containing `trxID`) is discarded; `payments.py` never writes `provider_trx_id` (grep: only read at `bkash.py:105`); thus `bkash.refund` always raises "no bKash reference" (L121-124). The same class of gap exists for Stripe (`provider_charge`/`provider_intent` never written, but `refund()` falls back to `Session.retrieve(provider_ref).payment_intent`, so Stripe refunds work) and PayPal (`provider_capture_id` only via webhook).
- **P-03 (refund before durable idempotent ledger) — CONFIRMED.** `refund_online` (L223-236) checks `order.payment_status=='paid'` and `amount<=order.total` (**not** minus prior refunds), then `issue_refund` (L238-272) calls `adapter.refund(...)` (L254) *before* `commerce.book_refund` (L258); no refund-intent row, no provider idempotency key, no lock: two concurrent requests both pass the read-only checks and both hit the provider. Provider failure after a successful provider call (e.g. exception in `book_refund`) leaves money moved with no ledger row. The returns path has the same shape: `accounts.py:407-411` calls `issue_refund` before the return row is marked settled (L445), so two staff clicking "refunded" can double-refund (the settled-state guard at L384-385 is read-then-write).
- **P-04 (item refund ignores conditional update result) — CONFIRMED.** `commerce.py:1676` (`await db.orders.update_one({'id':id,'payment_status':order['payment_status']}, {...})`) discards the result; the code continues to update the transaction, email, restock (~L1677-1690) even if `matched_count==0` after the provider refund (L1670) already ran. Additional defects in the same function: `refunded_amount` is `$set` from a stale read (L1672 `total_refunded=refunded+amount`) rather than `$inc`; `payment_transactions.status` is set to the **order** payment status string (`refunded|partially_refunded`) (L1678); while `issue_refund` sets `refunded_amount` to the single amount (`payments.py:268` `'refunded_amount': amount`) instead of accumulating — two code paths disagree.
- Additional (NEW) payment defects, all in the verify path:
  1. **Client-chosen gateway object, not bound to the order (HIGH).** `stripe.verify` uses `params.get("session_id") or transaction.provider_ref` (`stripe.py:89`); `paypal.verify` uses `params.get('token') or provider_ref` (`paypal.py:113`); `bkash.verify` uses `params.get('paymentID') or provider_ref` (`bkash.py:102`). `verify_payment` forwards the customer-controlled `data.params` (`payments.py:123,132`). A buyer who has paid a cheap order can submit that order's Stripe `session_id` (or PayPal order id) against an expensive unpaid order and get it marked paid: nothing checks `session.client_reference_id/metadata.order_id` or that `amount_total==order.total` (only SSLCommerz checks amount/tran_id). Exploitability requires knowing a paid session id (own purchase) — **logic confirmed from source, not exercised**.
  2. No amount/currency check for Stripe, PayPal, bKash on verify or webhook (`payments.py:183-190` ignores `event['amount']`).
  3. PayPal capture step missing (above).
  4. `webhook` 'refunded' handler marks whole order refunded for partial refunds (L196-208).
  5. `provider_config` snapshot (non-secret config) copied into each transaction row (L84) — harmless but stale; `/admin/transactions` projects it out (L282).
  6. `verify_payment` has no rate limit (not in `RATE_LIMITS`) and each call can trigger a provider API round-trip (bKash execute) — DoS/cost vector.

### 7.3 Draft → release → rollback mechanics (`release_engine.py`; legacy `cms.py`)
- Storage: `site_workspace{id:'store', version:int, draft:{theme, site, pages:{slug:Page}}, active_revision:<release id>, history:[release ids], updated_at, published_at}` (one doc; the history array grows unbounded) and immutable `site_releases{id, bundle:{theme,site,pages}, created_at, author, summary, kind:'initial'|'publish'|'rollback', source_revision}`. Bundle validated by `Bundle` model: `pages` ≤80, must contain `home`, keys equal slugs (L30-39).
- Save draft: `PUT /api/admin/builder` (`content.update` + `theme.update`) = compare-and-set on `version` (L136-139, 153-160); 409 on conflict. Per-document legacy saves `PUT /api/admin/documents/{id}` go through `save_legacy` → same CAS (L134-140).
- Publish: `POST /api/admin/builder/publish` (`content.publish` + `theme.publish`): requires `data.version==current.version` and at least one `pending_changes` (schema-normalized diff over auth/footer/header/checkout/theme/pages, L56-71), then `commit()` inserts a new release first and flips `active_revision` with a CAS on `{version, active_revision}` (L162-171) → atomic pointer switch; failure leaves live site untouched.
- Rollback: `POST /api/admin/builder/rollback {revision_id, version}` creates a **new** release copying the old bundle (`kind:'rollback'`, L205-212). Restore-to-draft: `/restore` (copies bundle into draft). History list ≤200 (L186).
- Public read: storefront gets the live release bundle (`catalog.py` `/api/store`, `cms.py:19-26` for pages); preview via short-lived token (`previews{id, document_id, token_hash, expires_at +30 min, revoked}`, `cms.py:117-125`) or `?preview=`/`X-Voltora-Preview` handled by `isolation.py`.
- **Dead/retired code**: `cms.publish` (`cms.py:75-85`) raises 409 immediately and the rest of the function is unreachable; `cms.new_page` has unreachable code after `return` (L69-73); `publishing_jobs.schedule` (L18-19) raises "retired" with unreachable body, while the cron receiver `/api/cron/publish` (needs `WEBHOOK_CRON_SECRET`) and `run_due` remain wired. Release data **excludes** products, settings and commerce data, so rollback never reverts catalog/pricing.
- Arbitrary caps that contradict the new requirement of "no arbitrary limits": 80 pages (`cms.py:~60`, `release_engine.py:33`), 60 sections/page, 12/6/10 header blocks, 6 footer columns, 20 shipping zones, 10 payment methods, 30 currencies, 5 tiers, 100 variants, 24 images, 15 nav links (`schemas.py` throughout).

## 11. Defects found beyond the prior audit

(Severity is my estimate; "confirmed" = logic confirmed by reading code, not by running it.)

**Payments / money**
1. **HIGH – verify trusts client-supplied gateway object ids** (`stripe.py:89`, `paypal.py:113`, `bkash.py:102`, forwarded from `payments.py:123,132`); no order/amount binding → cross-order payment reuse (details §4.3).
